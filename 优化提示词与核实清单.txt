一、修复报告生成时的跨用户数据读取风险
提示词：
检查 ReportService 中补查父任务的逻辑。查询祖先任务时必须同时限制当前 userId，不能只按任务 ID 查询。确认构建报告 Prompt 所用的任务和跟进记录都属于当前用户。请只处理这一项，完成后说明修改内容和验证结果。

历史核实：代码检查通过。同步和 SSE 生成均传递 userId，祖先任务及跟进查询均增加归属过滤。未进行真实跨用户场景验证。

二、修复任务超过 500 条后数据不完整
初始提示词：
检查 TaskList.vue 和 Home.vue 对 /api/tasks/page 的调用。目前它们可能只请求第一页、最多 500 条，导致更多任务被静默遗漏。
请修复为能获取完整任务数据，并为后端分页参数设置合理上限、处理非法页码和页大小。保留现有任务树、筛选、首页统计和重点任务展示行为。完成后说明修改内容和验证结果。

补充提示词：移除 25,000 条的加载上限
继续修复任务分页加载不完整的问题。当前 web/src/api/tasks.ts 的 fetchAllTaskRows 最多只拉取 50 页（25,000 条），超过后仍会截断。
请移除会导致任务被截断的固定页数上限，让任务列表和首页能够加载后端返回的全部任务；同时避免一次性并发发送过多请求，可采用分批或有限并发分页。保留按 ID 去重，并确保加载失败时明确提示，不要把不完整结果当成完整数据展示。完成后说明修改内容和验证结果。

补充提示词：消除后端 1,000 页上限的影响
继续修复任务全量加载问题。目前后端将页码钳制到 1000 页，前端遇到连续重复页就停止，并将结果当成完整数据，导致超过 500,000 条任务时仍会遗漏。
请调整前后端分页方案，消除固定页码上限造成的数据截断，可采用游标分页。保留有限并发和按 ID 去重；遇到重复页或分页无法推进时，应明确报错，不能当成加载成功。为分页提供稳定排序，避免创建时间相同导致跨页重复或遗漏。
只处理这一项，完成后验证跨页边界、超过原上限及请求失败的情况，并说明修改内容和验证结果。

历史核实：已改用 /api/tasks/scroll 游标分页，按 create_time DESC、id DESC 排序，串行拉取，首页和任务列表均接入。不再受旧 /page 接口的 1,000 页上限影响。前端类型检查通过；模拟验证 0、500、501、25,001、500,001 条及请求失败、重复页、缺失游标、空页却声明还有数据均通过。未进行真实数据库的大数据量验证；实际容量受浏览器内存和加载时间约束。

三、实现真正的退出登录
提示词：
检查并修复退出登录流程。目前前端可能只清除本地登录状态，服务端 Session 仍然有效。
请增加服务端退出登录接口，使当前 Spring Session JDBC 会话失效，并清除对应的会话 Cookie。前端退出时调用该接口，成功或失败后都清理本地登录状态并跳转登录页；若请求失败，应明确提示服务端会话可能未注销。
验证退出后使用原会话 Cookie 无法访问受保护接口，同时确保其他独立会话不受影响。只处理这一项，完成后说明修改内容和验证结果。

补充提示词：真实接口验证
验证“真正退出登录”的实际效果：
1. 为同一账号建立两个独立登录会话 A、B，分别保存 Cookie。
2. 使用会话 A 调用 POST /api/auth/logout，确认响应清除了会话 Cookie。
3. 手动携带退出前保存的 A Cookie 请求 /api/auth/info，确认 HTTP 状态码为 401。
4. 使用 B Cookie 请求同一接口，确认仍可正常访问。
使用本地测试环境和现有测试账号，不修改业务数据，不输出密码或完整 Cookie。请报告各步骤的实际结果；若环境无法运行，明确说明尚未验证的部分，不要以代码检查代替实际验证。

历史核实：代码检查、前端类型检查和成功/网络失败/401 的模拟验证通过；随后在 http://127.0.0.1:8080 进行了真实接口验证，全部通过：同账号 A/B 独立会话均登录成功；A 退出返回 HTTP 200、业务 code 200，响应清除 SESSION Cookie（Max-Age=0）；重放 A 的原 Cookie 得到 HTTP 401、业务 code 401；B 仍返回 HTTP 200、业务 code 200。验证会话已清理，未修改业务数据。验证前只读确认现有演示账号已使用 BCrypt，以避免登录触发明文密码升级。曾因沙箱限制误判服务不可达，后在沙箱外确认运行并完成上述验证。

四、登录和注册成功时轮换 Session ID
提示词：
检查并修复登录和注册流程中的 Session 固定风险。
登录或注册成功后，在写入登录用户信息前轮换 Session ID，兼容现有 Spring Session JDBC。认证失败时不要写入登录态。
验证时先建立匿名会话并保存原 Cookie，再完成登录，确认 Session ID 已变化、新 Cookie 能正常访问受保护接口，而原 Cookie 返回 HTTP 401。注册成功路径也应执行相同的轮换逻辑，同时确保其他独立会话不受影响。
只处理这一项，保留现有退出登录行为。完成后说明修改内容和实际验证结果，未能验证的部分明确标注。
